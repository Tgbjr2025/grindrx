# Building GrindrX

> **Inherited from upstream Open Grind.** The `nix run .#build-android` path and
> the reproducibility table below are upstream's, and the `flake.nix` it refers to
> **is currently known not to work for an Android release build** — the
> Nix-provided Android environment fails to resolve the Tauri plugin subprojects
> (`No matching variant of project ':tauri-plugin-biometric'`). The v0.1.33 APK was
> built with a hand-assembled toolchain instead; that is the path that was
> actually verified end-to-end. See
> [README.md → Build from source](./README.md#build-from-source) for the working
> recipe and the exact toolchain versions.

GrindrX ships a [Nix flake](./flake.nix) that pins the entire Android toolchain — Rust, the JDK, the Android SDK, the NDK, Gradle, and Bun — so any contributor on Linux or macOS can produce an identical build in an identical environment.

## Prerequisites

- [Nix](https://nixos.org/download) >= 2.18

No other dependencies are needed, everything is bundled into Nix flake.

## Quickstart

Only Android release builds are supported as of May 15th, 2026.

```bash
nix run .#build-android
```

> [!NOTE] First time you run `nix develop` or `nix run` in Open Grind's repository, Nix will download
> and setup about 3 GB environment, which might take some time, depending on your internet connection speed.

Output: `src-tauri/gen/android/app/build/outputs/apk/universal/release/app-universal-release-unsigned.apk`.

You will need to [enable APK signing](#signing) in order to install this APK on an Android device, otherwise attempts to install it will throw "App not installed as package appears to be invalid." error.

If you use [direnv](https://direnv.net/), the bundled [.envrc](./.envrc) activates the dev shell automatically when you `cd` into the repository.

## Trusting the build environment

Before running any build or verification steps, you are trusting several components. This section explains what each is, where it comes from, and how to independently verify it.

### Verifying Nix and flake.lock

[flake.lock](./flake.lock) pins every flake input to an exact content hash: JDK, Android SDK, NDK, Rust, Bun.

1. Confirm the nixpkgs revision in flake.lock resolves to a commit on the official NixOS/nixpkgs repository:

```bash
grep -A3 '"nixpkgs"' flake.lock # note the "rev" value
# verify it exists at https://github.com/NixOS/nixpkgs/commit/<rev>
```

2. Also read [flake.nix](./flake.nix) itself to verify build steps

### Verifying the Gradle wrapper jar

The wrapper jar at `src-tauri/gen/android/gradle/wrapper/gradle-wrapper.jar` is committed and pinned to Gradle 8.14.5.

```bash
shasum -a 256 src-tauri/gen/android/gradle/wrapper/gradle-wrapper.jar
```

Compare against [Gradle's published checksums](https://gradle.org/release-checksums/) for 8.14.5 (`7d3a4ac4de1c32b59bc6a4eb8ecb8e612ccd0cf1ae1e99f66902da64df296172`).

## Do not build the Gradle project directly

**Always drive an Android build through the Tauri CLI** (`bun run tauri android
build --apk`, or `bun tauri android init` to regenerate the project). Do **not**
`cd src-tauri/gen/android && ./gradlew assembleRelease`.

The generated Gradle project carries **three** copies of the version, and only the
Tauri CLI keeps them in agreement:

| File                                                        | `versionName` | `versionCode` | Who reads it                                            |
| ----------------------------------------------------------- | ------------- | ------------- | ------------------------------------------------------- |
| `src-tauri/tauri.conf.json`                                 | `0.1.33`      | `1068`        | the Tauri CLI, and `generate_context!` on the Rust side |
| `src-tauri/gen/android/app/tauri.properties`                | `0.1.33`      | `1068`        | `app/build.gradle.kts:40-41` → the actual APK           |
| `src-tauri/gen/android/app/src/main/assets/tauri.conf.json` | `0.1.33`      | `1068`        | embedded in the APK's assets                            |

Both generated files are **autogenerated artifacts**. They are committed, so they
drift the moment anyone edits `tauri.conf.json` and forgets to regenerate — and
`tauri.properties` is the one that decides the shipped `versionCode`, because
`build.gradle.kts` reads _it_ and not `tauri.conf.json`.

This is not hypothetical. Before v0.1.33 those copies said
`0.1.32 / 1065 / autoIncrement=true` while `tauri.conf.json` said
`0.1.33 / 1068 / autoIncrement=false`, so a direct Gradle build produced
**versionCode 1065** — _lower_ than the 1068 in the source config. F-Droid and Play
reject that as a downgrade, so the update is silently never offered.

`assets/tauri.conf.json` also carries a second copy of the Content Security
Policy, and it had drifted too: it was missing `object-src 'none'`,
`frame-src 'none'; base-uri 'self'; form-action 'none'`, which the source config
has. **Which copy the Android _runtime_ actually applies is not established** — the
Rust side compiles the _source_ config in via `generate_context!`, so the compiled
binary is expected to carry the strong CSP, but the asset copy is a real second
copy sitting in the APK and nobody has verified the merge. Both now carry the
identical full policy, so the question is moot until the next divergence.

**Checklist before shipping an APK:**

1. `package.json`, `tauri.conf.json` and `tauri.properties` all say the same
   `versionName`, and `tauri.conf.json` + `tauri.properties` agree on `versionCode`.
2. `autoIncrementVersionCode` is `false` in **both** config copies. It overrides
   the explicit `versionCode`, it consumes one code per build invocation, and it is
   **non-monotonic** across builds — a rebuild has previously produced a _lower_
   code than the build before it.
3. Read the real value back from the artifact, every time:
   ```bash
   aapt2 dump badging <apk> | grep ^package
   ```
4. Confirm the two `tauri.conf.json` copies still have the same `app.security.csp`:
   ```bash
   diff <(jq -r .app.security.csp src-tauri/tauri.conf.json) \
        <(jq -r .app.security.csp src-tauri/gen/android/app/src/main/assets/tauri.conf.json)
   ```

If any of these disagree, regenerate with `bun tauri android init` rather than
hand-editing the generated files — and if `init` produces something wrong, fix
`tauri.conf.json` and re-run it.

> ### ⚠️ Two of those three files are gitignored — they will NOT travel
>
> `src-tauri/gen/android/app/.gitignore` (Tauri-generated) excludes:
>
> ```
> /src/main/assets/tauri.conf.json
> /tauri.properties
> ```
>
> So `tauri.properties` and `assets/tauri.conf.json` are **local build artifacts**,
> not repository contents. A fresh clone has neither, and `bun tauri android init`
> generates both from `tauri.conf.json`.
>
> **This is why the skew was invisible in review.** The two stale copies are not
> committed, so `git diff` never showed them — they only exist in a working tree
> that has run `tauri android init`, i.e. on whichever host last did. The v0.1.33
> APK was built on the macOS host, so **that host's copies may still be stale even
> after this repository is fixed**, and a hand-off that skips `tauri android init`
> will build from whatever is lying around.
>
> Practical consequence: `tauri.properties` is un-committable, so it cannot be
> fixed in the repository. It has to be regenerated on the build host:
>
> ```bash
> bun tauri android init     # regenerates tauri.properties + assets/tauri.conf.json
> cat src-tauri/gen/android/app/tauri.properties   # then read it back
> ```
>
> And the `aapt2 dump badging` check in the checklist above is not optional
> polish — it is the **only** check that can catch this class of skew, because the
> files that cause it are not in version control.

## Smoke-test the release APK

The release build type runs **R8 minification** (`isMinifyEnabled = true` in
`app/build.gradle.kts`). That is not a no-op for this app: `MainActivity` exposes
three JavaScript bridges that JS reaches **by name only**, via
`WebView.addJavascriptInterface` (`MainActivity.kt:205-207`):

| Bridge name           | What it drives                             | If R8 strips it                                  |
| --------------------- | ------------------------------------------ | ------------------------------------------------ |
| `__AndroidInsets`     | edge-to-edge inset padding                 | UI sits under the status bar / nav bar           |
| `__DiscreetMode`      | the weather-icon "discreet" launcher alias | the discreet-mode toggle silently does nothing   |
| `__BackgroundService` | the keep-alive foreground service          | no message notifications while the app is closed |

R8 sees no Kotlin or JS call site for any of them, so it will strip them if it
happens to. `app/proguard-rules.pro` now carries a
`-keepclassmembers class * { @android.webkit.JavascriptInterface <methods>; }` rule
for exactly this reason — but **a keep rule is not proof it took effect**, and the
failure mode is silent: the APK builds, installs, launches, and only the bridged
features are missing.

So a release APK must be **installed and exercised**, not just built. Minimum
checklist on a real device before calling a release good:

- [ ] Keyboard opens in chat; the composer is fully visible and the message list
      is not under the system bars → `__AndroidInsets`
- [ ] Settings → App → Security → discreet mode toggles the launcher icon → `__DiscreetMode`
- [ ] Background service toggle starts a foreground notification, and a message
      arriving with the app closed raises a notification → `__BackgroundService`
- [ ] `<input type="file">` opens the document picker **and returns a file**
      (this is the `FileProvider`; `res/xml/file_paths.xml` must scope it — see
      the comment in that file)
- [ ] A photo taken with the camera is reachable from the picker, and the app
      sends it

To confirm R8 actually kept the bridges rather than trusting the checkbox, look at
the R8 mapping/report in `app/build/outputs/mapping/release/`, or decompile
`MainActivity` out of the release APK and confirm the three interface classes and
their annotated methods are present.

**No GrindrX release has been device-tested for this.** v0.1.33 is recorded as
"builds, is signed, not tested on a physical device" (see `README.md`). Treat
every bridged feature as unverified on any APK until the list above is ticked.

## Verifying a published release

GrindrX's official APK is signed with the fork's own JKS — certificate
`22:D6:88:9E:…:8D:4C:01`, see [KEYS.md](./KEYS.md). (This section previously
hard-coded the **upstream** governance certificate `2805fdd8…c3658c` and fetched
from the **upstream** release page, so it failed at step 3 against every GrindrX
APK that has ever shipped. Both are corrected below.) No access to the signing key
is required to verify that the published binary was built from the source in this
repository.

Android's v2/v3 signing block lives in a dedicated region between the last zip entry and the central directory; v1 (JAR) signatures live in `META-INF/*.SF`, `*.{RSA,EC,DSA}`, and modify `MANIFEST.MF`. Everything else — dex, native libs, resources, manifest, assets — is byte-identical between a signed and an unsigned build of the same source on the same toolchain.

All tools below ship with the dev shell — `nix develop` and you're ready.

```bash
nix develop

# 1. Reproduce the unsigned APK locally
git checkout v<tag>
nix run .#build-android
LOCAL=src-tauri/gen/android/app/build/outputs/apk/universal/release/app-universal-release-unsigned.apk

# 2. Fetch the published signed APK
#    GitHub  (canonical mirror): https://github.com/Tgbjr2025/grindrx/releases/tag/v<tag>
#    Forgejo (canonical repo):   https://git.dominusaxis.com/dominus/grindrx/releases
#    e.g.   gh release download "v<tag>" -R Tgbjr2025/grindrx -p GrindrX-v<tag>.apk
PUBLISHED=./GrindrX-v<tag>.apk

# 3. Confirm JKS certificate
#    This is the fork's own signing certificate, the same one README.md, FDROID.md
#    and KEYS.md publish. A mismatch here means the APK is not a GrindrX release.
EXPECTED="22d6889ef07459a20919d48afffe7ed7a4e3903039e15542767cedcdff8d4c01"
ACTUAL=$(apksigner verify --print-certs "$PUBLISHED" \
  | grep "Signer #1 certificate SHA-256 digest" \
  | awk '{print $NF}')

if [ "$ACTUAL" = "$EXPECTED" ]; then
  echo "✓ APK certificate matches GrindrX's release JKS"
else
  echo "✗ APK: certificate fingerprint mismatch" >&2
  echo "  expected $EXPECTED" >&2
  echo "  actual   $ACTUAL" >&2
  exit 1
fi

# 4. Confirm the content reproduces
apk_content_hash() {
  unzip -Z1 "$1" \
    | grep -vE '^META-INF/(MANIFEST\.MF|[^/]+\.(SF|RSA|EC|DSA))$' \
    | while IFS= read -r entry; do
        printf '%s  %s\n' \
          "$(unzip -p "$1" "$entry" | sha256sum | cut -c1-64)" \
          "$entry"
      done
}
if diff <(apk_content_hash "$LOCAL") <(apk_content_hash "$PUBLISHED"); then
  echo "✓ APK hash checksum matches, local build reproduces the published APK exactly"
else
  echo "✗ APK hash checksum mismatch, local build does not match the published APK" >&2
  exit 1
fi
```

If step 3 succeeds, the published APK was signed with GrindrX's own release key.

If step 4 succeeds, the published APK was built from this commit, on this
toolchain, byte-for-byte apart from the signing block.

**Step 4 has a real caveat, and step 3 is the one to trust.** Byte-identical
reproduction requires the exact same JDK, Android SDK/NDK, Gradle, Rust and Bun
versions listed in the table below, and the same path/environment. The v0.1.33
APK was in fact built by hand on a macOS host, not through `nix run .#build-android`
— see [README.md → Note on the Nix flake](./README.md#build-from-source) and the
prerequisites table — so a Nix-shell rebuild of that specific APK is **not known
to reproduce it byte-for-byte**, and a step-4 diff is not currently evidence of
tampering. Treat a step-4 failure as "my toolchain differs from the release
build's", and confirm that first. Step 3 has no such caveat: the certificate
fingerprint is either right or it is not.

**The repository's recorded test result:** the cert in step 3 was verified
against the published v0.1.33 artifact on both hosts (see `memory/MEMORY.md`).
Step 4 has never been run to completion for any GrindrX release.

## Signing

Signing is optional and only needed for production builds (if you're going to install the APK on your Android device). You don't need to follow signing instructions if you're just [verifying release binaries reproducibility](#verifying-a-published-release). Do not commit anything about your keystore.

`keytool` is part of the JDK, so it is already available inside `nix develop` — you do not need to install it.

1. Create a JKS once (from inside `nix develop`):

```bash
keytool -genkey -v \
  -keystore ~/.config/open-grind/release.jks \
  -alias open-grind \
  -keyalg EC \
  -groupname secp256r1 \
  -sigalg SHA256withECDSA \
  -validity 20000
```

2. Copy [contrib/keystore.properties.example](./contrib/keystore.properties.example) to a private location such as `~/.config/open-grind/keystore.properties` and fill it in.

3. Build with:

```bash
OPEN_GRIND_KEYSTORE_PROPERTIES=/path/to/keystore.properties \
  nix run .#build-android
```

For example, on macOS you could pass `OPEN_GRIND_KEYSTORE_PROPERTIES=~/.config/open-grind/keystore.properties` or `OPEN_GRIND_KEYSTORE_PROPERTIES="/Users/you/.config/open-grind/keystore.properties"`, on Linux `OPEN_GRIND_KEYSTORE_PROPERTIES="/home/you/.config/open-grind/keystore.properties"`

The build copies the properties file into the Gradle project for the duration of the build and removes it on exit. If `OPEN_GRIND_KEYSTORE_PROPERTIES` is unset, the release build is produced unsigned — this is the mode F-Droid uses on its reproducible-build servers, and the mode third parties use to verify a published release (see below).

## Reproducibility

Every input that affects the output bytes is pinned in exactly one place:

| Component                               | Where it's pinned                                                |
| --------------------------------------- | ---------------------------------------------------------------- |
| nixpkgs                                 | `flake.lock`                                                     |
| Rust toolchain                          | `rust-toolchain.toml`                                            |
| JDK                                     | `flake.nix` (`jdk21_headless`)                                   |
| Android compileSdk / minSdk / targetSdk | `src-tauri/gen/android/gradle.properties`                        |
| Android build-tools                     | `src-tauri/gen/android/gradle.properties`                        |
| Android NDK                             | `src-tauri/gen/android/gradle.properties`                        |
| Android CMake                           | `src-tauri/gen/android/gradle.properties`                        |
| Android Gradle Plugin                   | `src-tauri/gen/android/build.gradle.kts`                         |
| Gradle distribution                     | `src-tauri/gen/android/gradle/wrapper/gradle-wrapper.properties` |
| Kotlin                                  | `src-tauri/gen/android/build.gradle.kts`                         |
| Bun                                     | nixpkgs pin (via `flake.lock`)                                   |
| Tauri CLI                               | `package.json` / `bun.lock`                                      |
| JS deps                                 | `bun.lock`                                                       |
| Cargo deps                              | `src-tauri/Cargo.lock`                                           |

The `opengrind.android.*` keys in `gradle.properties` are read by both Gradle and `flake.nix`. Bump them there once and both consumers pick up the new value.

### Refreshing the lock

```bash
nix flake update
```

### Cargo / JS hygiene

Inside `nix develop`:

```bash
cargo build
bun install --frozen-lockfile
```

`bun.lock` is the only lockfile in this repository (`docs/bun.lock` is a separate
workspace), and `package.json` declares `"packageManager": "bun@1.3.11"`. Use
`bun install --frozen-lockfile` so a CI or developer install fails loudly on a
lockfile mismatch instead of silently re-resolving and rewriting `bun.lock`. A
bare `bun install` is the thing that produces drift.

Never run `cargo update` or `bun update` without intentionally bumping dependencies and reviewing the diff.

### Known gap: no Rust release profile

`src-tauri/Cargo.toml` has **no `[profile.release]`** section, so release builds
use Cargo's default: no LTO, `codegen-units = 16`, and **no `strip`**. For a
native library this size that is a meaningful APK-size and symbol-table cost.

This is a one-line-ish fix but `Cargo.toml` is not in this pass's changed-files
scope, so it is **reported, not applied**. Recommended, to be applied by whoever
owns `src-tauri/Cargo.toml`:

```toml
[profile.release]
lto = true            # cross-crate inlining; shrinks and speeds up the hot paths
codegen-units = 1     # needed for `lto = "fat"` to be worth it
strip = true          # drop the symbol table; `strip = "symbols"` also drops debuginfo
panic = "abort"       # optional: smaller, but changes abort-vs-unwind behaviour
opt-level = "s"       # consider, and measure: the hot path is reqwest/tokio, not ours
```

`panic = "abort"` and `opt-level` are **product/build decisions, not obvious
defaults** — `panic = "abort"` removes unwinding, which changes behaviour if any
dependency relies on catching a panic, and `opt-level = "s"` will cost throughput
on the msgpack/WebSocket paths. `lto`, `codegen-units` and `strip` are safe and are
the recommended minimum. **Verify the size delta and the 17 Rust tests after
changing this**, and re-run the device smoke test — LTO has historically been
where "it compiled but does not work" bugs appear.
